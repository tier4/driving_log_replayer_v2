# Autowareにおける各種加速度系列の比較と特性まとめ

本ドキュメントでは、Autowareの各種トピックおよび信号処理から得られる異なる系列の加速度信号について、その物理的意味、遅延特性、ノイズレベル、およびパラメータ同定における優位性を整理してまとめています。

---

## 1. 加速度系列の比較一覧 (Quick Reference)

| 信号系列名 | データソース | 遅延 (対実機運動) | ノイズレベル | 特徴・発生メカニズム | 主な用途・推奨度 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`/localization/acceleration`**<br>(実機トピック) | IMU / EKF速度等の<br>二次処理フィルタ値 | **大 (約 80 ms)** | 低 (滑らか) | EKF処理後にノイズ除去用のローパスフィルタ(LPF)を通すため、位相が遅れる。 | 制御入力のフィードバック等。<br>⚠️同定用には遅延補正が必要。 |
| **`kinematic_diff`**<br>(EKF速度の数値微分) | `/localization/kinematic_state`<br>の `vx` を数値微分 | **極小 (ほぼ 0 ms)** | 中 | EKF（カルマンフィルタ）で平滑化された速度を微分。適度なLPFで実用に耐える。 | **パラメータ同定に最も推奨**。<br>（適合スコアが劇的に改善） |
| **`velocity_diff`**<br>(車輪速の数値微分) | `/vehicle/status/velocity_status`<br>の `lon_vel` を数値微分 | **極小 (ほぼ 0 ms)** | **極大** | CAN由来の生のホイールスピードを微分するため高周波ノイズが非常に乗りやすい。 | 一部車両の通信ズレリスクあり。<br>あまり推奨しない。 |
| **`position_2diff`**<br>(位置の2回微分) | `kinematic_state` の位置<br>$(x, y)$ を時間で2回微分 | **極小 (ほぼ 0 ms)** | **極大 (スパイク多)** | 位置情報の離散差分を2回行うため、極めてノイズに弱く、強い平滑化が必須。 | 物理的な運動確認の補助用。<br>同定には非推奨。 |

## 2. 各系列の詳細解説

### ① `/localization/acceleration` (実機トピック)
* **概要**: Autowareが自己位置推定モジュールの一部として配信する加速度のトピックです。
* **メリット**: すでにローパスフィルタ(LPF)等の処理が施されているため非常に滑らかで、制御モジュール等が直接フィードバック制御に使うのに適しています。
* **デメリット**: フィルタ処理の特性上、実際の車両運動に対して **一貫して約 80 ms 程度の時間遅れ（位相遅れ）** が発生しています。これを考慮せずにシミュレーションモデルの同定パラメータ（無駄時間など）を適合すると、モデルの無駄時間パラメータが過大に推定され、クローズドループシミュレーションの精度悪化を招きます。

### ② `kinematic_diff` (EKF速度の数値微分)
* **概要**: 自己位置推定結果である `/localization/kinematic_state` の進行方向速度 `vx` を時間差分で数値微分し、中心移動平均（LPF）を適用したものです。
* **メリット**: EKF（拡張カルマンフィルタ）によってIMUと車輪速が最適に融合された滑らかな速度をベースにするため、ノイズが比較的抑えられています。また、追加の遅延フィルタを通さないため、**時間的な遅れがほぼありません**。
* **結論**: これを用いることで、車両運動の立ち上がりタイミングを正確に捉えることが可能となり、Optunaを用いた縦方向適合スコア（誤差）が **`26.52` から `18.39` へと劇的に向上** しました。

### ③ `velocity_diff` (車輪速の数値微分)
* **概要**: 車両CANから直接送信される `/vehicle/status/velocity_status` の速度 `lon_vel` を数値微分したものです。
* **デメリット**: 生の車輪速センサー（ホイールエンコーダー）のパルスから計算されるため、路面振動やスリップによる微小なノイズが微分処理によって何倍にも増幅され、非常にトゲトゲした波形になります。また、一部の車両プラットフォームではCANゲートウェイのタイムスタンプ同期ズレ（数秒単位のズレ）が発生するリスクがあります。

### ④ `position_2diff` (位置の2回微分)
* **概要**: `kinematic_state` の空間上の軌跡 $(x, y)$ と進行方向（yaw角）から速度ベクトルを算出し、それをもう一度微分して得られる加速度です。
* **デメリット**: 位置の差分を2回繰り返すため、極めてノイズに弱くスパイクが発生しやすいです。強い移動平均フィルタ（窓幅広め）をかけてトレンドを合わせる必要がありますが、数値検証や物理妥当性のバックアップ指標として用いられます。

## 3. 遅延（タイムラグ）の発生要因

相互相関（Cross-Correlation）を用いた372件のバグ解析により、実機トピック `/localization/acceleration` は数値微分値に対して **平均 74 ms 〜 86 ms 遅れている** ことが証明されました。

> [!NOTE]
> **遅延の発生メカニズム**
> 1. **処理順序のラグ**: Autoware内部で、センサー生データ ➔ EKFによる速度推定（`kinematic_state`）➔ 加速度算出（`acceleration`）というパイプライン処理が順次実行されるため、後段のトピックほど処理時間遅れが累積します。
> 2. **ローパスフィルタ(LPF)の特性**: 制御の安定性を高めるためにかけられているノイズ除去フィルタは、その遮断周波数に応じて信号の位相を右（未来方向）へシフトさせます。

## 4. 振幅（ピーク値）の差異とその要因

車輪速（`velocity_status` や `kinematic_state`）から算出した微分加速度は、IMUやトピックの加速度に比べて**最大ピーク値が小さくなりやすい**特性があります。これは以下の物理現象によるものです。

```
【急ブレーキ時の挙動の差】

   ▼ IMU（慣性計測）の場合:
     車体傾き(ノーズダイブ) ➔ 重力Gの一部が前後Gに回り込む ➔ 加速度が「過大」に計測される
     [ 実際の加減速G ] + [ 重力 g × sin(前傾角θ) ]

   ▼ 車輪速（数値微分）の場合:
     タイヤの滑り(スリップ)やヨレ(変形) ➔ 回転数変化がマイルドに ➔ 加速度が「過小」に計測される
     [ 実際の路面対地速度の変化 ] ➔ フィルタでさらに丸められる
```

1. **ローパスフィルタの平滑効果**: 微分ノイズを消すためのフィルタによって、瞬間的なスパイクが平らになり、ピーク値が小さく見えます。
2. **タイヤのスリップと変形**: 加減速の力がタイヤと路面の間に加わる際、タイヤのヨレや微小スリップによって速度変化の伝達がマイルドになります。
3. **サスペンションのピッチ挙動（重力加速度の回り込み）**: 慣性センサー(IMU)は、車両が急制動で前傾（ピッチ）した際、地球の重力加速度（$9.8 \text{ m/s}^2$）の一部を「減速度」として誤って計測してしまいます。そのため、トピックの加速度はピッチ挙動の分だけピークが過大になりがちです。

## 5. 同定パイプラインにおける推奨プラクティス

> [!IMPORTANT]
> **物理パラメータ同定における推奨設定**
> 
> * **デフォルトの推奨設定**: `ACCEL_SOURCE = "kinematic_diff"` 
>   - 位相遅れが 0 秒であり、車両の物理的な応答遅延（無駄時間 `acc_time_delay`）を純粋に同定できます。
> * **トピックを利用する場合 (`"accel"`)**:
>   - 従来のトピックを使用する場合は、今回の実装で整備された `ACCEL_DELAY_MAP["accel"] = 0.080` を有効にして、同定結果から**処理遅延（80ms）を差し引く補正**を必ず有効にしてください。これにより、制御上の遅延と物理ラグを分離できます。
