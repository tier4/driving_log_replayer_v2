# driving_log_replayer_v2 for ROS 2 Autoware.Universe

driving_log_replayer_v2 is a ROS package that evaluates the functionality of Autoware.Universe

## Requirements

- ROS 2 humble or Jazzy
- Python 3.10 or 3.12

### Optional

If you want to change the rosbag format from ros1 to ros2.

- [rosbags](https://gitlab.com/ternaris/rosbags)
  - `pip3 install rosbags`

## Installation

Use colcon build

```shell
colcon build --symlink-install --cmake-args -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCMAKE_BUILD_TYPE=Release --packages-up-to driving_log_replayer_v2
```

### How to install driving_log_replayer_v2_cli package

Use pipx **Do not use pip**

```shell
# install
pipx install git+https://github.com/tier4/driving_log_replayer_v2.git

# upgrade
pipx upgrade driving-log-replayer-v2

# uninstall
pipx uninstall driving-log-replayer-v2
```

## (For Developer) Release Process

This package uses `catkin_pkg` to manage releases.

Refer [this page](https://wiki.ros.org/bloom/Tutorials/ReleaseCatkinPackage)

### Release command

Direct push to `develop` and `main` is not allowed, so the release is done through pull requests.
Only the signed tag is created locally by a maintainer.

1. Create a release branch from `develop`, update the files, and push it.

   ```shell
   git checkout develop
   git pull origin develop
   git checkout -b chore/prepare-release-<version>
   # create change log
   catkin_generate_changelog
   # edit CHANGELOG.rst
   # update package version in pyproject.toml (and uv.lock)
   # edit ReleaseNotes.md
   git commit -s -am "chore: update changelog for <version>"
   # update CHANGELOG.rst and package.xml, then commit and create a git tag
   catkin_prepare_release --version <version> --no-push
   # the signed tag is created in step 4, so delete the tag created by the command
   git tag -d <version>
   git push origin chore/prepare-release-<version>
   ```

2. Create a pull request to `develop` and merge it.
3. Create a pull request from `develop` to `main`, and merge it with a **merge commit** (do not squash or rebase).
   The documentation is deployed by merging to `main`.
4. Create and push the signed tag on `main`.

   ```shell
   scripts/tag_release.sh <version>
   ```

## (For Developer) Workflow Dependency Lockfile

GitHub Actions dependencies are locked in `.github/workflows/actions.lock` (see [Workflow dependency lockfiles](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles), public preview).
The lockfile records the commit SHA of every action used in `.github/workflows/`, including actions that are called inside other actions.
Do not edit the lockfile by hand. It is generated by the GitHub CLI extension `gh actions-lock`.

Refer [this page](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies) for details.

### Install

```shell
gh extension install github/gh-actions-lock
# upgrade the extension
gh extension upgrade gh-actions-lock
```

### Update the lockfile

Run the command from the repository root after you add, remove or change an action in `.github/workflows/`.

```shell
# lock all workflows
gh actions-lock
# lock a single workflow
gh actions-lock .github/workflows/pre-commit.yaml
```

The command also rewrites `uses:` references to the resolved version (e.g. `actions/checkout@v5` to `actions/checkout@v5.1.0`).
Review the whole diff and commit the workflow files together with `actions.lock`.

If a tag has moved to another commit, check the history of the upstream repository first. If the move is legitimate, relock it.

```shell
gh actions-lock --relock
```
